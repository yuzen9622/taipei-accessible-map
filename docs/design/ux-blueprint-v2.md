## 0. 現況診斷：為什麼「不符合大眾、不會讓人一直用」

以下每一條都對應到具體檔案，不是印象評論。

### 0.1 沒有產品外殼，只有一張地圖

`src/app/[lng]/page.tsx` → `ClientMap` → 全螢幕地圖 + 浮層。整個 app 只有 3 個真正的路由（`/`、`/reset-password`、`/verify-email`），其他所有內容都塞進 `BottomSheet` 的 15 種面板模式或 Dialog 裡。

後果：任何「非地圖」的內容（使用說明、我的貢獻、設定、個人化）永遠只能擠在 380px 寬的面板或 380px 寬的 dialog 裡。這是「產品感薄」的結構性根因——不是配色問題，改配色救不回來。

### 0.2 冷啟動零敘事

`src/components/Splash.tsx` 只有 logo + `t("title")`，沒有一句話說明這是什麼、為誰做的。Splash 結束後直接進地圖，然後瀏覽器彈出定位權限請求——使用者在完全不知道這個 app 要幹什麼的狀態下被要求交出位置。

grep 全專案沒有任何 `onboarding` / `firstVisit` / `hasSeen` 狀態，確認：**首次使用流程完全不存在。**

### 0.3 登入是功能性表單，不是入口

[AuthDialog.tsx:216](../../src/components/shared/AuthDialog.tsx#L216) 是 `max-w-[380px]` 的 dialog：logo 40px + 標題 + tabs + Google 按鈕 + 表單。問題：

- 沒有價值敘述。唯一一句是「登入無障礙智慧地圖，享有完整功能」（`:232`）——「完整功能」是什麼？沒說。
- 沒有訪客路徑。實際上這個 app 不登入也能查地圖、規劃路線，但 dialog 完全沒告訴使用者，讓人以為必須註冊。這是註冊漏斗最大的流失點。
- 註冊成功只有一段純文字 + 兩顆按鈕（`:281-310`）。使用者剛完成註冊，情緒最高的時刻，畫面給的是最平淡的回應。
- 硬編碼中文字串（`:226-234`、`:284-285`、`:314`、`:347` 等）——英文版整個登入流程是中文，i18n 破洞。

### 0.4 首頁是功能清單，不是意圖入口

[HomeContent.tsx](../../src/components/BottomSheet/HomeContent.tsx) 的垂直順序：搜尋框 → 路線規劃 → 快捷列（6 色膠囊）→ 收藏 → 最近搜尋。

- 六個分類色（`:62-98`：橙/琥珀/靛/綠/天藍/玫瑰）同時以 `/10` 底 + 彩色文字出現，加上主色藍、SOS 紅，畫面同時有 8 個色彩系統競爭。Apple/Linear 的做法相反：底層極度中性，彩色只在「資料本身帶語意」時出現。
- 「自訂快捷」編輯入口（`:274-291`）在首頁第二排最顯眼處。新使用者第一次打開就看到「自訂」，這是把設定當功能賣。
- 完全沒有個人化。沒有家/公司、沒有「你常去的地方」、沒有情境建議。收藏與最近搜尋是唯二的個人化，而且都要先用過才會有內容——冷啟動使用者看到的是空的。

### 0.5 說明是文件，不是教學

[HelpDialog.tsx:155](../../src/components/shared/HelpDialog.tsx#L155) 把「功能說明」「台北專屬」「回報教學」「FAQ + 資料來源致謝」放進同一個 dialog 的四個 tab。資訊優先級錯了：使用者要學怎麼用，卻跟 TDX/環境部 logo 混在一起。而且入口在帳號 dropdown 裡（`AccountLogin.tsx`），新使用者永遠找不到。

### 0.6 沒有回饋迴路 = 沒有回訪動機

`getMyHazardReports()` 與 `confirmHazardReport()` 兩個 API 已經存在（[a11y.ts:105,112](../../src/lib/api/a11y.ts#L105)），但前端沒有任何地方讓使用者看到「我回報過什麼」「我的回報幫到了誰」。使用者花力氣拍照回報障礙，得到的回應是一個 toast，然後永遠消失。

這是「不會一直用」的直接原因。無障礙地圖的資料護城河靠使用者貢獻，但目前的設計沒給貢獻者任何回報。

## 1. 三個布局方案（結構層）

### 方案 A：地圖優先浮層（Map-First Overlay）— 現況精緻化

保留現有結構：全螢幕地圖 + 桌面左側 Icon Rail + 手機 Bottom Sheet。只做視覺升級（收斂配色、統一圖示、重排首頁順序）。

- 改動範圍：`HomeContent.tsx`、`globals.css`、各 Panel 樣式。不動路由、不動狀態機。
- 工期估：3–5 天
- 優點：風險最低，v1.0 視覺規範可直接套用完。
- 缺點：**沒有解決 §0.1 的結構性問題**。說明/貢獻/設定永遠塞在窄面板。個人化內容沒有版位可放。做完會「比較好看」，但不會「讓人想一直用」。
- 適用：如果只有 1 週時間、或這是給評審 demo 用的短期任務。

### 方案 B：App Shell + 地圖分頁（Shell + Map）— **建議採用**

引入產品外殼概念。4 個主分頁，其中「探索」是全螢幕地圖，其餘 3 頁是有完整版面的一般頁面。

```
手機（<1024px）                      桌面（≥1024px）
┌─────────────────────┐             ┌──┬────────────┬──────────────┐
│                     │             │  │            │              │
│    地圖 / 頁面內容    │             │R │  Layer 2   │     地圖      │
│                     │             │a │   面板      │              │
│  ┌───────────────┐  │             │i │  (380px)   │              │
│  │  Bottom Sheet │  │             │l │            │              │
│  └───────────────┘  │             │72│            │              │
├─────────────────────┤             │px│            │              │
│ 探索 路線 貢獻 我的  │  ← Tab Bar   └──┴────────────┴──────────────┘
└─────────────────────┘                 ↑ Rail 底部放 4 個主分頁切換
```

四個分頁：

| 分頁 | 內容 | 為什麼獨立成頁 |
|---|---|---|
| **探索** | 全螢幕地圖 + 搜尋 + 篩選 + 地點詳情（現有主介面） | 核心功能，維持全螢幕 |
| **路線** | 路線規劃 / 路線比較 / 我的常用路線 / 離線口袋卡 | 路線比較需要並排空間，塞在 380px 面板裡看不清楚 |
| **貢獻** | 回報障礙 + 確認設施狀態 + 我的貢獻紀錄與影響力 | §0.6 的回饋迴路，需要獨立版位 |
| **我的** | 無障礙需求檔案 / 帳號 / 設定 / 使用說明 / 緊急聯絡人 | 把現在「dropdown → dialog → tabs」三層深的結構攤平成一頁 |

- 改動範圍：新增 `src/app/[lng]/(shell)/` route group + 4 個 route、`BottomSheet` 狀態機收斂（只保留探索頁需要的模式）、`AccountLogin` dropdown 拆解成 `/me` 頁。
- 工期估：2.5–3 週
- 優點：解決 §0.1。每個內容類型都有適合的版位。這是 Google Maps / Citymapper / Transit 的通用結構，使用者不需要學。桌面與手機共用同一套資訊架構（Rail 底部 = 手機 Tab Bar），不會出現兩套心智模型。
- 缺點：工期最長，需要動 `useMapStore` 的 `sheetMode` / `activeRailPanel` 狀態機（v1.0 §5.2 剛定案的規則要重新對照）。
- 風險控制：分頁可以漸進上線——先加 Tab Bar 與「我的」頁（把設定搬出來），「貢獻」「路線」頁後續補。探索頁完全不動。

### 方案 C：對話優先（Assistant-First）

AI 助理當主入口，地圖降為「回答的視覺化」。首屏是一個大輸入框 + 建議問句（「我坐輪椅，想從這裡到台北車站，避開有階梯的路」），地圖在回答後才展開。

- 改動範圍：重寫首屏、`useAIChat` 升為主要狀態機。
- 工期估：2 週
- 優點：差異化最強。「無障礙需求」是天生適合自然語言表達的問題——輪椅寬度、能不能爬三階、要不要有電梯，這些用篩選器要點十下，用一句話講完。
- 缺點：**不建議當作整體結構**。三個致命問題：(1) AI 延遲或失敗時整個 app 不可用；(2) 對不熟 AI 的長者使用者是障礙而非捷徑；(3) 「我想看看附近有什麼」這種無明確意圖的瀏覽行為，對話式介面處理很差。
- **建議**：把方案 C 的精神放進方案 B 的探索頁——首頁輸入框同時吃「地點搜尋」與「自然語言提問」，使用者打「台北車站」走搜尋，打「附近有無障礙廁所嗎」走 AI。一個輸入框兩種模式，不需要使用者先選。

### 決策建議

**採用方案 B 作為骨架，把方案 C 的統一輸入框放進探索頁，方案 A 的視覺收斂規範全案適用。**

理由：使用者的抱怨是「不符合大眾、不會讓人一直用」。「不符合大眾」是視覺問題（方案 A 能解），「不會讓人一直用」是結構問題（只有方案 B 能解）。只做 A 會回到同一個抱怨。

## 2. 全站畫面清單與版面規劃

以下 S0–S12 是完整畫面清單。標註 `[新]` 的是目前完全不存在的畫面。

### S0 — 冷啟動 Splash

現況：logo + 標題。

新版：
```
        [ logo 88px ]

     無障礙智慧地圖
  找得到、進得去、到得了

     ●●●○  (載入進度)
```
- 加一句 tagline（i18n key `tagline`），讓使用者第一眼知道這是什麼。
- 載入進度用三段式（地圖底圖 / 定位 / 設施資料），不要無限轉圈。轉圈讓人不知道要等多久，分段進度讓人願意等。
- 維持 `useReducedMotion` 判斷（現有實作正確）。

### S1 `[新]` — 首次啟動導覽（未登入也要走）

**這是投報率最高的單一改動。** 四步全螢幕，可跳過，狀態存 `localStorage["onboarding.v1"]`。

**Step 1／這是什麼**
```
┌──────────────────────────────┐
│                              │
│      [ 插圖：地圖 + 輪椅 ]      │
│                              │
│   為行動不便者設計的地圖        │
│                              │
│   不只告訴你怎麼走，          │
│   還告訴你進不進得去。         │
│                              │
│   ● ○ ○ ○                    │
│   ┌──────────────────────┐   │
│   │      開始設定         │   │
│   └──────────────────────┘   │
│        先四處看看             │
└──────────────────────────────┘
```

**Step 2／你的需求**（最重要的一步）
```
   哪些情況符合你？可以多選

   ┌─────────┐ ┌─────────┐
   │ ♿      │ │ 🦯      │
   │ 使用輪椅 │ │ 視覺障礙 │
   └─────────┘ └─────────┘
   ┌─────────┐ ┌─────────┐
   │ 助行器   │ │ 行動較慢 │
   └─────────┘ └─────────┘
   ┌─────────┐ ┌─────────┐
   │ 推嬰兒車 │ │ 陪同他人 │
   └─────────┘ └─────────┘

   這會影響路線怎麼算，

```
- 6 個選項，多選，2 欄卡片（不是 checkbox 清單——卡片點擊面積大，符合 44px 觸控目標，也比清單好看）。
- 這一步直接決定：路線演算法權重、地圖預設篩選、地點詳情頁欄位排序。**必須真的生效**，不能只是問問看——問了不用是最傷信任的設計。
- 選「視覺障礙」時，完成後直接提示是否開啟語音優先模式（現有 `Voice/` 元件已具備能力）。

**Step 3／為什麼需要定位**
```
   ┌────────┐
   │   📍   │
   └────────┘
   我們需要你的位置

   ✓ 找出你附近的無障礙設施
   ✓ 從你現在的位置規劃路線
   ✓ 緊急時讓聯絡人知道你在哪

   位置只在使用時取得，
   不會持續追蹤、不會分享給第三方。

   ┌──────────────────────┐
   │      允許定位         │
   └──────────────────────┘
       手動輸入位置也可以
```
- **關鍵**：先解釋再要求系統權限。目前是進地圖後瀏覽器直接彈窗，使用者在沒有 context 的情況下按拒絕，之後很難挽回（瀏覽器權限被拒後不會再問）。
- 「手動輸入位置」是真的要能用的降級路徑，不是安慰劑。

**Step 4／試試看**
```
   設定完成

   從這三件事開始：

   ┌──────────────────────────┐
   │ 🚻 找附近的無障礙廁所      │  → 點了直接執行
   ├──────────────────────────┤
   │ 🧭 規劃一條無階梯路線      │
   ├──────────────────────────┤
   │ 💬 問 AI：這附近好走嗎？   │
   └──────────────────────────┘

        直接開始使用
```
- 三張卡片是**可執行的**，不是說明文字。點了就進入該功能並帶好參數。第一次成功使用的體驗決定留存。

### S2 — 登入 / 註冊（重做）

從 380px dialog 改為**全屏／大型 dialog 雙欄**。

桌面（≥1024px，`min-w-[880px]`）：
```
┌───────────────────────┬──────────────────────┐
│  [logo] 無障礙智慧地圖  │      登入   註冊      │
│                       │  ─────────           │
│  ✓ 收藏跨裝置同步      │  ┌────────────────┐  │
│    手機存的地點，       │  │ 使用 Google 繼續│  │
│    電腦也看得到         │  └────────────────┘  │
│                       │   ──── 或 ────       │
│  ✓ 緊急聯絡人          │  ┌────────────────┐  │
│    SOS 時自動通知家人   │  │ 電子郵件        │  │
│                       │  ├────────────────┤  │
│  ✓ AI 記住你的偏好     │  │ 密碼            │  │
│    不用每次重講需求     │  └────────────────┘  │
│                       │  ┌────────────────┐  │
│  ────────────────     │  │      登入       │  │
│  不登入也能查地圖       │  └────────────────┘  │
│  和規劃路線 →          │                      │
└───────────────────────┴──────────────────────┘
```
手機：左欄內容收成頂部三行帶勾的短句，表單在下。

必修項：
1. **左欄三條具體價值**，取代現在的「享有完整功能」。每條都是使用者實際會在意的事。
2. **訪客路徑明示**（左下角），連到不登入直接用。這一條會直接改善註冊漏斗——讓人知道可以不註冊，反而更多人願意先用、用了才註冊。
3. **註冊成功改為慶祝態**：勾勾動畫 + 「你的帳號已建立」+ 信箱圖示 + 「我們寄了驗證信到 xxx@xxx」+ 主要 CTA「打開信箱」/ 次要「重寄」。取代現在的純文字段落。
4. **全部字串進 i18n**。現在 `AuthDialog.tsx` 有 12 處以上硬編碼中文。
5. 密碼欄加顯示/隱藏切換 + 註冊時即時強度提示（`validatePassword` 已存在，只是現在只在送出後才給錯誤）。

### S3 `[新]` — 註冊/登入後的使用說明

這是你點名要的「登入註冊後應該要有使用說明（之後就不用了）」。

分兩層，兩層都是一次性：

**3a. 歡迎卡（首頁頂部，可關閉）**
```
┌────────────────────────────────────┐
│ 👋 歡迎，小明            [×]       │
│                                    │
│ 三個地方帶你熟悉：                   │
│ ① 搜尋列 — 找地點或直接問 AI         │
│ ② 篩選鈕 — 只看你需要的設施          │
│ ③ 右下紅鈕 — 緊急時長按求救          │
│                                    │
│  [ 帶我看一遍 ]   [ 我自己來 ]      │
└────────────────────────────────────┘
```
- 出現在 `HomeContent` 最上方，關閉後寫入 `localStorage["welcomeCard.v1.dismissed"]`，不再出現。
- 「帶我看一遍」啟動 3b。

**3b. Coach marks（3 步聚光燈）**

只指 3 個 UI，不多。每步：半透明遮罩 + 目標元件挖空高亮 + 氣泡說明 + 「下一步 / 略過」。
1. 搜尋列（`PlaceInput`）— 「打地名找地點，或直接問『附近有無障礙廁所嗎』」
2. 無障礙篩選（Rail 的 `a11y` / 首頁 a11y chip）— 「只顯示你需要的設施類型」
3. SOS 鈕（右下角）— 「長按 2 秒發送求救，會通知你的緊急聯絡人」

完成或略過都寫 `localStorage["coachMarks.v1.done"]`。

**無障礙要求（不可省）**：
- coach marks 必須可鍵盤操作（Tab/Enter/Esc），Esc = 略過全部。
- 每步用 `aria-live="polite"` 播報說明文字，不能只靠視覺高亮。
- `prefers-reduced-motion` 時取消聚光燈的動態位移，改為直接切換。
- 螢幕閱讀器使用者應在 Step 1 就被提示「可按 Esc 略過導覽」。

**「之後就不用了」的完整規則**：
| 狀態鍵 | 何時寫入 | 何時重置 |
|---|---|---|
| `onboarding.v1` | S1 完成或跳過 | 只在「我的 → 重看新手導覽」手動重置 |
| `welcomeCard.v1.dismissed` | 使用者按 × 或完成 3b | 同上 |
| `coachMarks.v1.done` | 3b 完成或略過 | 同上 |
- 版本號後綴讓未來大改版時可以重新導覽一次（`v2` 換鍵），不用清掉使用者所有偏好。
- 登入後應同步到後端 `userConfig`，讓換裝置不會重跑（見 §5 後端需求）。

### S4 — 狀態頁樣板（verify-email / reset-password / 錯誤頁）

### S5 — 探索首頁（Home Sheet 重排）

現況順序：搜尋 → 路線規劃 → 6 色快捷 → 收藏 → 最近。

新版順序（依「使用者打開 app 想做什麼」的機率排序）：

```
┌────────────────────────────────────┐
│ 🔍 搜尋地點，或問我任何事       🎙 │  ← 統一輸入框（方案 C 精神）
├────────────────────────────────────┤
│                                    │
│  🏠 家        🏢 公司       ＋      │  ← 個人化捷徑（新）
│  15 分鐘      32 分鐘               │     顯示即時所需時間
├────────────────────────────────────┤
│  ⌖ 你附近                          │  ← 情境區塊（新）
│  ┌──────────┐┌──────────┐┌───────  │     依 a11y profile 動態決定
│  │ 無障礙廁所││  電梯     ││ 斜坡   │     卡片內容，橫向滑動
│  │  120m    ││  80m     ││       │
│  └──────────┘└──────────┘└───────  │
├────────────────────────────────────┤
│  ⚠ 你常經過的忠孝東路有新的障礙回報  │  ← 主動提示（新，有才顯示）
├────────────────────────────────────┤

└────────────────────────────────────┘
```

關鍵改動：
1. **統一輸入框**：地點搜尋 + AI 提問同一個入口。輸入框右側常駐麥克風。判斷規則：命中 autocomplete → 走搜尋；使用者按 Enter 而無選中項且字串含疑問詞或超過 8 字 → 走 AI。
2. **家/公司捷徑**：顯示「現在過去要多久」而不只是名稱。這是 Google Maps 留存的核心設計——每天打開都有新資訊。
3. **情境區塊取代 6 色快捷列**：不再讓使用者從六個分類裡選，而是根據 onboarding 的 a11y profile 直接顯示他要的東西。輪椅使用者看到「無障礙廁所/電梯/斜坡」，視障使用者看到「導盲設施/有聲號誌」。
4. **快捷膠囊降級**：從 6 色 `/10` 底改為中性底（`bg-muted`），只有 icon 保留分類色。收進第二層（「更多」或下滑）。這一條直接解決 §0.4 的色彩噪音。
5. **「自訂快捷」移出首頁**，搬到「我的 → 介面偏好」。
6. **路線規劃入口**移到 Tab Bar 的「路線」分頁，首頁不再需要那顆大按鈕。

### S6 — 地點詳情

核心原則：**無障礙資訊必須在第一屏**，不能混在一般營業資訊裡。

```
┌────────────────────────────────────┐
│ [照片]                             │
├────────────────────────────────────┤
│ 台北市立圖書館 總館                  │
│ 圖書館 · 營業中 · 800m              │
│                                    │
│ ┌────────────────────────────────┐ │  ← 無障礙評分卡（第一屏）
│ │ 無障礙資訊                      │ │
│ │                                │ │
│ │ ✓ 無障礙入口    已確認 · 3天前  │ │
│ │ ✓ 無障礙廁所    已確認 · 3天前  │ │
│ │ ⚠ 電梯          維修中 · 今天   │ │
│ │ ? 引導設施      尚無資料        │ │
│ │                                │ │
│ │ 這裡的資訊正確嗎？ [確認] [回報] │ │  ← 眾包確認入口
│ └────────────────────────────────┘ │
│                                    │
│ ┌──────────┐ ┌──────────┐         │
│ │ 規劃路線  │ │  收藏     │         │
│ └──────────┘ └──────────┘         │
├────────────────────────────────────┤
│ 營業時間 / 電話 / 地址 / 評論        │  ← 一般資訊往下
└────────────────────────────────────┘
```

- **三態設計**：`已確認`（綠勾 + 誰在何時確認）／`有問題`（琥珀 + 回報內容）／`尚無資料`（灰問號）。**不要用「有/沒有」二元**——「沒資料」跟「確認沒有」是完全不同的意思，混在一起會害人白跑一趟。這是無障礙產品的誠信底線。
- 每項都顯示「最後確認時間」。三天前確認的電梯跟三年前的資料，可信度差很多，使用者有權知道。
- 「確認/回報」按鈕在卡片內，不用跳頁——降低貢獻門檻是資料量的關鍵。

### S11 — 未登入態的處理

app 不登入也能用，這件事必須一致地表達：

| 功能 | 未登入 | 觸發登入的時機 |
|---|---|---|
| 搜尋 / 瀏覽地圖 / 篩選 | ✓ 完整可用 | 不需要 |
| 路線規劃 / 導航 | ✓ 完整可用 | 不需要 |
| a11y 需求檔案 | ✓ 存 localStorage | 提示「登入可跨裝置同步」（不阻斷） |
| 收藏地點 | ✓ 存 localStorage | 收藏第 4 個時提示同步（不阻斷） |
| 回報障礙 / 確認設施 | ✗ | 點擊時彈登入，說明「回報需要帳號以維護資料品質」 |
| 緊急聯絡人 / SOS 通知 | ✗ | 進入時彈登入 |
| AI 記憶 | ✗ | 對話中提示 |

原則：**能不擋就不擋**。只在「行為會影響其他使用者」（回報）或「需要後端存資料」（聯絡人、記憶）時才要求登入，並且每次都說明為什麼。

### S12 — 空狀態與錯誤態（全站）

目前散落各處，需要統一。每個空狀態都是「邀請」而不是「道歉」：

| 情境 | 現況 | 新版 |
|---|---|---|
| 沒有收藏 | 整區不顯示（`HomeContent:396`） | 「收藏常去的地方，下次一鍵前往」+ 收藏按鈕位置提示 |
| 沒有搜尋紀錄 | 整區不顯示 | 顯示 3 個熱門無障礙地點建議 |
| 附近沒有設施 | 未知 | 「這附近還沒有資料 — 你知道哪裡有嗎？」+ 回報入口 |
| 定位失敗 | toast | inline 卡片 + 「手動輸入位置」 |
| 離線 | 未知 | 頂部持久橫幅 + 「已存的口袋卡仍可使用」 |
| API 失敗 | toast | inline + 重試按鈕（不要只給 toast，toast 會消失） |

**規則：整區不顯示是最差的選擇**。使用者不會知道那裡本來有東西，也不會知道怎麼讓它出現。

## 3. 新功能提案

依「對留存的影響 ÷ 實作成本」排序。

### P0-1 無障礙需求檔案（A11y Profile）

**是什麼**：使用者的行動需求設定（輪椅/助行器/視障/行動較慢/嬰兒車/陪同者），在 S1 Step 2 建立，全站生效。

**生效點**：
- 路線演算法：避開階梯權重、電梯必要性、最大坡度、可接受步行距離
- 地圖預設篩選：直接顯示相關設施類型
- 地點詳情：無障礙欄位排序（輪椅使用者先看廁所/入口，視障使用者先看引導設施）
- 首頁情境區塊內容
- AI 助理 system context（不用每次重講「我坐輪椅」）

**為什麼是 P0**：這是「這個 app 認識我」的唯一來源，也是所有個人化的基礎。成本低（一個設定物件 + 幾處條件判斷），效果貫穿全站。

### P0-2 設施狀態眾包確認（「還能用嗎？」）

**是什麼**：對單一設施一鍵回報「還能用 / 不能用」，附最後確認時間。

**情境**：使用者到了大安站，看到 3 號出口電梯正常，點一下「還能用」。下一個要來的輪椅使用者看到「2 小時前有人確認可用」。

**為什麼是殺手級**：政府開放資料只告訴你「這裡有電梯」，不會告訴你「電梯今天在維修」。這個顆粒度的即時性只有使用者社群能提供，Google Maps 做不到（他們沒有專注在這群使用者上）。這是這個產品真正的護城河。

**實作**：`confirmHazardReport` 已存在但只針對 hazard report。需要後端加設施層級的確認 API（見 §5）。

### P0-3 貢獻回饋迴路

**是什麼**：S9 分頁 + 「你的回報幫助了 N 人」的具體回饋。

**為什麼**：這是回訪動機。無障礙社群的貢獻意願很高（因為切身相關），但目前的設計把貢獻做成單向的黑洞。

### P1-1 路線可信度分數

**是什麼**：每條路線標示「已驗證比例」，並列出資料來源（政府資料 / N 位使用者確認 / 演算法推測）。

**為什麼**：誠實揭露不確定性。對輪椅使用者，「不確定」是可以規劃的（多留 20 分鐘、帶人同行），「假裝確定然後出錯」是災難（到現場才發現進不去，可能就回不了家）。

### P1-2 離線口袋卡

**是什麼**：出門前把路線存成離線包，含逐步指示、電梯位置、無障礙廁所、目的地電話、備用路線。

**情境**：在捷運地下層沒訊號，但仍需要知道哪個出口有電梯。

**為什麼**：行動不便者最大的焦慮是「到現場才發現不行」。離線卡把焦慮換成準備。技術上是 localStorage/IndexedDB + Service Worker，不需要後端。

### P1-3 導航中行程分享

**是什麼**：導航開始時可分享即時位置給緊急聯絡人，抵達自動停止。

**為什麼**：現有 SOS 是「出事後求救」，這是「出事前預防」。對獨自出門的使用者和他們的家人都是安心來源。`sos.ts` 與 `EmergencyContactsManager` 已有基礎。

### P2-1 語音優先模式

**是什麼**：全語音操作模式——搜尋、選擇路線、導航全程語音，畫面只作為輔助。

**為什麼**：`Voice/` 元件已存在，但目前是「附加功能」。對視障使用者應該是「主要模式」。S1 Step 2 選了「視覺障礙」就主動提議開啟。

### P2-2 陪同者模式

**是什麼**：切換成「幫別人查」——為家人/被照顧者規劃路線，使用他們的 a11y profile 而非自己的。

**為什麼**：照服員、家屬是重要的次要使用者群，目前完全沒被考慮。S1 Step 2 已有「陪同他人」選項，這是它的延伸。

### P2-3 無障礙路線眾包編輯

**是什麼**：使用者可標記某段人行道的實際狀況（寬度不足/斜度過大/被機車占用）。

**為什麼**：這是資料層的長期投資，也是最難的（需要地圖編輯 UI + 審核機制）。建議在 P0-2 的確認機制跑順、有活躍貢獻者之後再做。

## 4. 實作順序建議

以「每個階段結束都能上線、都有可感知的改善」為原則切。

| 階段 | 內容 | 估時 | 結束時使用者感受到什麼 |
|---|---|---|---|
| **Phase 1** | S1 首次啟動導覽 + P0-1 a11y profile（存 localStorage）+ S0 Splash tagline | 5–7 天 | 「這個 app 知道我是誰、為我調整過」 |
| **Phase 2** | S2 登入註冊重做 + S3 歡迎卡與 coach marks + S4 狀態頁樣板 | 4–6 天 | 「進得來、看得懂、知道怎麼開始」（直接回應你點名的需求） |
| **Phase 3** | S5 首頁重排 + 視覺收斂（6 色降級為中性）+ S12 空狀態 | 5–7 天 | 「畫面清爽了，而且每天打開都有新資訊」 |
| **Phase 4** | 方案 B 外殼：Tab Bar + S10 我的頁（設定攤平） | 5–7 天 | 「找得到東西了」 |
| **Phase 5** | S9 貢獻頁 + P0-2 設施確認 + P0-3 回饋迴路 | 7–10 天 | 「我的貢獻有意義」← 留存的轉折點 |
| **Phase 6** | S6 地點詳情無障礙卡 + S7 路線比較 + P1-1 可信度 | 7–10 天 | 「資訊可信、決策有依據」 |
| **Phase 7** | P1-2 離線卡 + P1-3 行程分享 + P2-1 語音優先 | 依需求排 | |

Phase 1–3 完全不需要後端改動，可以立刻開工。Phase 5 起需要後端配合（見 §5）。

## 5. 需要後端配合的清單

以下是前端無法自己解決、需要轉達給後端工程師的需求。已標註目前狀態。

### 5.1 `UserConfig` 擴充（Phase 1 想跨裝置同步時需要）

現有 `src/types/user.d.ts` 的 `UserConfig` 只有 `language / darkMode / themeColor / fontSize / notifications / highContrast`。需要新增：

```ts
interface UserConfig {
  // ...現有欄位
  a11yProfile?: {
    mobility: ("wheelchair" | "walker" | "slow" | "stroller" | "none")[];
    vision?: "blind" | "low_vision" | "none";
    avoidStairs: boolean;
    requireElevator: boolean;
    maxSlopePercent?: number;
    maxWalkMeters?: number;
    companionMode?: boolean;
  };
  onboarding?: {
    version: string;        // "v1"
    completedAt: string;    // ISO
    coachMarksDone: boolean;
  };
}
```
- 前端可先只用 localStorage 上線（Phase 1 不阻塞），但登入使用者換裝置會重跑導覽。
- 需要的 API 行為：`PATCH` 現有的 user config 端點時接受這兩個新欄位並原樣回傳。

### 5.2 設施層級狀態確認 API（Phase 5，P0-2 依賴）

現有 `POST /api/v1/a11y/reports/{id}/confirm` 只能確認「障礙回報」。P0-2 需要確認「設施本身」：

```
POST /api/v1/a11y/facilities/{osmId}/status
body: { status: "working" | "broken" | "blocked", note?: string, photoUrl?: string }

GET /api/v1/a11y/facilities/{osmId}/status
→ { status, lastConfirmedAt, confirmCount, recentReports: [...] }
```
並在現有 `GET /api/v1/a11y/nearby-a11y` 與 `GET /api/v1/a11y/place` 的回應中加入 `lastConfirmedAt` / `confirmCount` / `currentStatus`，供 S6 的三態評分卡顯示。

### 5.3 待確認設施清單（Phase 5，S9 依賴）

```
GET /api/v1/a11y/facilities/needs-confirmation?lat=&lng=&radius=
→ 依「距上次確認時間」排序的附近設施，供「附近待確認」區塊
```

### 5.4 貢獻影響力統計（Phase 5，P0-3 依賴）

```
GET /api/v1/a11y/contributions/me/stats
→ { reportCount, confirmCount, estimatedUsersHelped, recentImpact: [...] }
```
`estimatedUsersHelped` 的計算方式請後端定義（例如：受影響路段在回報後被重新規劃的次數）。**這個數字必須有真實依據**，前端不會自己編。

### 5.5 路線可信度（Phase 6，P1-1 依賴）

現有 `POST /api/v1/a11y/accessible-route` 的回應需加入每段路的資料來源與驗證狀態：

```ts
segments: [{
  // ...現有欄位
  dataSource: "government" | "osm" | "user_confirmed" | "inferred";
  lastVerifiedAt?: string;
  confirmCount?: number;
}]
```
前端據此算出整條路線的可信度百分比。

### 5.6 行程分享（Phase 7，P1-3 依賴）

現有 `sos.ts` 已有位置分享機制，需確認能否重用為「非緊急的行程分享」（不同的通知文案、抵達自動結束）。若不能重用需新端點。

## 6. 視覺收斂原則（與 v1.0 規範的關係）

`visual-design-spec.md` v1.0 的 token 系統、z-index 分層、圖示語意表**全部繼續有效**。本文件只補一條上位原則，它會影響 v1.0 §3 的分類色用法：

> **彩色只在資料本身帶語意時出現。分類不是語意。**

具體到程式碼：
- `HomeContent.tsx:62-98` 的六個 `bg-{color}/10 text-{color}` 快捷膠囊 → 改為 `bg-muted text-foreground`，只有 `<Icon>` 保留分類色。
- 保留彩色的情境：無障礙狀態（綠=已確認/琥珀=有問題/灰=無資料）、SOS 紅、路況障礙琥珀、環境資料本身的指標色。
- 桌面 Rail 啟用態的分類色維持（v1.0 §4.3 已規範「未啟用態中性、啟用態才上色」，方向正確）。

理由：使用者說「不符合大眾」。Apple/Linear/Vercel 的共同做法是底層極度中性、彩色極度節制。目前 8 個色彩系統同時競爭，每個元件都在喊「看我」，結果是沒有階層，讀起來累。

## 7. 待你決策的項目

1. **走哪個方案**：建議 B（外殼 + 地圖分頁）。若時間只有 1–2 週，先做 Phase 1–3（純視覺與 onboarding，不動結構），方案 B 的外殼延後。
2. **S1 導覽是否強制**：建議可跳過但預設走完（跳過鍵放右上角，不要太顯眼）。強制走完轉換率高但會激怒一部分人。
3. **未登入能不能用 a11y profile**：建議可以（存 localStorage）。這樣 onboarding 不需要先註冊，漏斗短很多。
4. **插圖風格**：S1 四步需要 4 張插圖。選項：(a) 純 Lucide icon + 幾何形狀（成本最低、風格最一致）(b) 客製線條插圖（質感最好、需外部資源）。建議 (a)，用 icon + 大色塊組合。
5. **後端需求的優先順序**：§5.1（config 擴充）最急且最簡單，建議先轉達這一項，其餘等 Phase 5 再談。
